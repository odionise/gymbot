# Линия силы — Telegram бот и Mini App

Бот присылает план по расписанию. Мини-приложение позволяет вести подходы, настраивать программу и видеть прогресс. План строится по четырёхнедельным мезоциклам: три недели накопления и неделя разгрузки.

Визуальные принципы Mini App и изученные референсы описаны в [DESIGN.md](DESIGN.md).
Задачи, реализованные функции и текущие ограничения собраны в [PROJECT_STATUS.md](PROJECT_STATUS.md).

## Что нужно для запуска

- Бот и токен от [@BotFather](https://t.me/BotFather).
- Домен с DNS-записью на VPS и открытыми портами 80/443.
- VPS с Docker Compose. Конфигурации 2 CPU / 4 ГБ достаточно для небольшого числа пользователей.

## Развёртывание

1. Скопируйте `.env.example` в `.env`. Укажите `BOT_TOKEN`, `DOMAIN`, `PUBLIC_URL=https://<домен>`, `POSTGRES_PASSWORD` и случайный `WEBHOOK_SECRET`. В `DATABASE_URL` укажите тот же пароль. Для публичного сервера поставьте `APP_ENV=production`, удалите или обнулите `DEV_TELEGRAM_ID`.
2. Выполните `docker compose up -d --build`. Caddy автоматически получит HTTPS-сертификат. API создаст таблицы и зарегистрирует webhook.
3. В BotFather настройте Main Mini App или кнопку меню на `PUBLIC_URL`. Отправьте боту `/start`, затем откройте приложение и создайте программу.
4. Проверьте `https://<домен>/health`, отправку `/today`, вход через Telegram и тестовое уведомление в выбранный день и время.

При запуске API применяет версионированные добавочные миграции схемы (`backend/app/migrations.py`). Перед обновлением сохраните резервную копию. Старые подходы остаются в истории с неизвестным RIR и не входят в новую аналитику жёстких подходов. Контейнер `backup` кладёт ежедневные дампы в `./backups` и хранит их 30 дней. Для защиты от потери VPS переносите копии на другое устройство или в объектное хранилище.

## Локальная разработка

### Быстрый просмотр через Docker

В корне проекта выполните в PowerShell:

```powershell
.\scripts\local.ps1 preview
```

Скрипт создаст игнорируемый Git файл `.env.local` со случайными секретами, соберёт локальные контейнеры и откроет приложение на `http://localhost:8080`. В режиме `preview` используется отдельный тестовый Telegram ID `123456789`; никаких сообщений бот не отправляет. Локальная PostgreSQL хранится в отдельном Docker volume. Изменения исходного кода требуют повторного запуска `preview` для пересборки.

Для проверки внутри Telegram создайте **отдельного тестового бота** через BotFather, впишите его токен в `TELEGRAM_BOT_TOKEN` файла `.env.local` на своём компьютере и выполните:

```powershell
.\scripts\local.ps1 telegram
```

Скрипт отключит вход по тестовому ID, запустит временный HTTPS-туннель Cloudflare и зарегистрирует webhook. Он выведет адрес Mini App. Отправьте тестовому боту `/start` в личном чате: ответ и кнопка меню откроют Mini App. Настройка Main Mini App в BotFather для этого пути не обязательна. Временный адрес меняется при повторном запуске туннеля; тогда снова выполните команду `telegram`. API в Telegram-режиме проверяет подпись `initData`. Сам интерфейс доступен по ссылке туннеля, поэтому используйте тестового бота и тестовые данные.

Для наполнения графиков локального предпросмотра примерами выполните:

```powershell
docker compose --env-file .env.local -f compose.local.yaml exec -T api python -m app.demo_seed
```

Скрипт добавляет к тестовому пользователю три программы с пометкой «ДЕМО» и 24 завершённые тренировки за восемь недель. Две недели отмечены как разгрузочные. Повторный запуск не дублирует записи; существующие тренировки не изменяются. Скрипт работает только при `APP_ENV=development` и настроенном `DEV_TELEGRAM_ID`.

Проверить контейнеры: `.\scripts\local.ps1 status`. Остановить их и удалить только локальный webhook: `.\scripts\local.ps1 stop`. Данные PostgreSQL при остановке сохраняются.

### Запуск без Docker

Локальный фронтенд работает без Telegram, если `DEV_TELEGRAM_ID` в `.env` совпадает с `VITE_DEV_TELEGRAM_ID` при запуске Vite. Этот режим доступен только при `APP_ENV=development`.

1. Запустите PostgreSQL и задайте локальный `DATABASE_URL` либо используйте SQLite (`sqlite:///./workout.db`) для быстрой разработки.
2. В `backend` создайте окружение Python 3.12+, установите `pip install -r requirements.txt` и запустите `uvicorn app.main:app --reload --port 8000`.
3. В `frontend` установите зависимости через `npm install` и запустите `VITE_DEV_TELEGRAM_ID=<ваш ID> npm run dev` (в PowerShell: `$env:VITE_DEV_TELEGRAM_ID='<ваш ID>'; npm run dev`). Откройте `http://localhost:5173`.
4. Для тестов сервера: из `backend` запустите `pytest`.

Если глобальный pnpm недоступен, тот же инструмент можно установить только в игнорируемое окружение проекта. Этот путь использован в текущей Windows-проверке:

Push-Location frontend
node ../.venv/frontend-tools/node_modules/pnpm/bin/pnpm.cjs install --frozen-lockfile --store-dir ../.venv/pnpm-store

Первая группа проверяет существующие сценарии, сохранность снимков и миграцию. Вторая содержит шесть приёмочных регрессий смешивания истории: на commit `57327b1` они падали без `xfail`, в итоговом прогоне этапа 1 прошли. Полный запуск без `-m` включает обе группы.

Общий helper `replace` в `tests/test_history.py` использует отдельный API замены. Он обновлён под согласованный контракт этапа 1; проверки пользовательского результата сохранены.

`tests/conftest.py` до импорта приложения принудительно задаёт development, пустой токен, отключённый dev-вход и служебный SQLite in-memory URL. Данные сценариев находятся во временных SQLite-файлах pytest. Календарные часы планирования, завершения, бота и аналитики устанавливаются на 26.10.2026 12:00 UTC и могут явно переводиться фикстурой `clock`. Синтетические завершения исходного набора используют дату сценария, поэтому порядок истории не зависит от скорости выполнения тестов.

Для проверки PostgreSQL нужен отдельный временный сервер. Не использовать рабочий DATABASE_URL. Пример, если Docker Engine уже доступен:

```powershell
docker run --detach --name gymbot-stage0-yourname --label gymbot.stage=stage0 --env POSTGRES_HOST_AUTH_METHOD=trust --env POSTGRES_USER=gymbot_test --env POSTGRES_DB=gymbot_test --publish 127.0.0.1:55443:5432 --mount type=tmpfs,destination=/var/lib/postgresql/data postgres:17-alpine
# После готовности pg_isready:
$env:GYMBOT_TEST_POSTGRES_URL = 'postgresql+psycopg://gymbot_test@127.0.0.1:55443/gymbot_test?connect_timeout=5'
.\.venv\Scripts\python.exe -m pytest -c backend/pytest.ini backend/tests/test_migrations_legacy.py -q --basetemp=.venv/pytest-stage0
```

Имя контейнера и свободный loopback-порт должны быть своими. Доступ без пароля допустим здесь только для одноразовых синтетических данных на loopback; контейнер не подключается к постоянному volume. Тест принимает только локальную БД с именем `gymbot_test`, создаёт собственную схему `gymbot_stage1_<uuid>` и удаляет только её. Проверяются исходные строки, связи, факты, тоннаж, неизвестные значения, доступность истории, повторное применение миграций 1–5 и восстановление синтетической копии. Без специального URL PostgreSQL-проверка получает явный `SKIPPED`. После проверки остановите и удалите только созданный вами тестовый контейнер; tmpfs при остановке теряется.

Для одновременного browser preview на одном компьютере нужны разные Compose project names, порты и volume. В `compose.local.yaml` закреплены общее имя и порт 8080, а `local.ps1 preview` может удалить ранее настроенный локальный webhook. Эти команды не являются изолированными по одному лишь расположению clone. На этапе 0 они не используются.

### Безопасная замена: этап 1

В программе есть отдельные действия «Изменить настройки» и «Заменить упражнение». Настройки сохраняют движение и базу результатов. Замена создаёт новое назначение и архивирует прежнее. Все созданные занятия сохраняют движение, цели и результаты; новое назначение применяется со следующего нового занятия. Отдельная замена на одно занятие в этот этап не входит.

При возвращении можно продолжить выбранную прежнюю базу или начать новую. Продолжение доступно только для того же `movement_id`, типа и места программы; одинаковые названия, разные места и дни не объединяются. Базы показывают дату, число занятий и последний собственный результат. Смешанная/неизвестная старая история сохранена, но не предлагается для продолжения автоматически. Для новой базы нужен явный старт; при продолжении старт подтверждается как запасной вариант, если нет подходящих обычных занятий. Ноль килограммов допустим при явном вводе; для временных типов нужны положительные минуты, автоматической прогрессии минут нет.

`Exercise.id` обозначает назначение, `slot_id` — постоянное место, `history_id` — базу результатов. Каждая замена получает новый `id`; старые назначения не активируются повторно. Сервер назначает эти идентификаторы; один слот имеет не более одного активного назначения. Перестановка меняет порядок, но не идентичности. Рекомендации и аналитика дополнительно проверяют движение/тип снимка, чтобы не смешивать старые записи, когда-то изменённые на месте. Новая база не удаляет факты, не обнуляет недельную нагрузку мышц и не переключает фазу. Формула веса и приоритет ПДО недели/возвращения сохранены.

| API | Контракт |
| --- | --- |
| `PUT /api/exercises/{id}` | Настройки того же движения; смена движения даёт `409`. |
| `GET /api/exercises/{id}/history-options?movement_id=…` | Только чтение доступных баз; не создаёт недели или занятия. |
| `POST /api/exercises/{id}/replace` | `{movement_id, history_mode: "new" / "resume", history_id: null / выбранный, settings}`. |

Для силового `settings` содержит все пять полей: `sets_count`, `medium_weight`, `weight_step`, `rep_min`, `rep_max`; для временного — только `duration_minutes`. Шаг веса должен помещаться в существующую точность БД: минимум 0,01 кг, до двух десятичных знаков; это проверка хранения, не новая методика оборудования. Ответ замены: `{exercise, history_mode, effective_from: "next_new_session", preserved_sessions_count}`. Повтор на старый `id` даёт `409` без дубля; после потерянного ответа следует обновить программу и сверить результат. Чужие идентификаторы дают `404`, некорректные параметры — `422`, несовместимая база — `409`.

Тип уже использованного движения в справочнике фиксирован; для другого типа создают другое движение. Исправление названия возможно и не меняет старые снимки. Новое поле `Movement.is_used` позволяет объяснить это в редакторе.

`SessionExercise.weight_step` теперь снимок, а не ссылка на текущую настройку. Для старых занятий он остаётся `NULL`: ручной ввод веса доступен, зависимые кнопки и подсказка следующего подхода отключены с пояснением. Силовые серии прогресса имеют непрозрачный `id`, отдельные `history_id`/`slot_id`/`movement_id` и понятный `label`; `id` серии не является идентификатором назначения для записи в API.

Перенос занятия с архивным/заменённым назначением временно запрещён (`409`); запись и завершение доступны. Запрос той же даты не меняет занятие. Политика пересчёта при переносе относится к отдельному календарному этапу. Лимит журнала 100 последних занятий на этом этапе не расширяется; сохранённые записи и их идентификаторы не удаляются.

Добавочная миграция **5** устанавливает известные `slot_id = id`, `history_id = id`, добавляет nullable-шаг снимка и уникальный индекс активного слота. Исторические факты, движения и неизвестные значения не восстанавливаются догадками. До будущего изменения существующей базы нужна проверенная резервная копия. Совместимость схемы добавочная, но старый код не понимает продолжение общей базы: сервер и клиент обновляются одной согласованной версией, а откат проверяется восстановлением копии. Два независимых варианта используют этот же контракт миграции 5 и свои базы; отдельную конфликтующую миграцию с тем же номером не выпускать.

Полный серверный прогон с PostgreSQL:

```powershell
$env:GYMBOT_TEST_POSTGRES_URL = 'postgresql+psycopg://gymbot_test@127.0.0.1:55443/gymbot_test?connect_timeout=5'
$env:PYTEST_DISABLE_PLUGIN_AUTOLOAD = '1'
.\.venv\Scripts\python.exe -m pytest -c backend/pytest.ini backend/tests -q --basetemp=.venv/pytest-stage1
```

В Windows-проверке использован официальный portable PostgreSQL **17.11** по ссылке со [страницы PostgreSQL для Windows](https://www.postgresql.org/download/windows/) на [EDB binaries](https://www.enterprisedb.com/download-postgresql-binaries). Он находится только в игнорируемом `.venv/pg17`, без службы, реестра или изменения Docker. Локальный сервер: `.venv/pg17/pgsql/bin/pg_ctl.exe -D .venv/pg17-data-runtime -l .venv/pg17-data-runtime/server.log -o "-h 127.0.0.1 -p 55443" -w start`; остановка: тот же `pg_ctl` с `-m fast -w stop`. Команды относятся только к созданному тестовому кластеру с loopback-конфигурацией. На другом компьютере сначала подготовьте собственный пустой кластер; не подставляйте рабочий PGDATA. Результаты проверок и реальные ограничения — в PROJECT_STATUS.md.

### Объяснение плана и ПДО: этап 2

В созданной силовой тренировке и истории раскрывается «Почему такой план?». Это сохранённые входы и результат расчёта: до трёх собственных обычных занятий, рабочие факты, медиана и округление веса, причина повторов/подходов, пределы недельного объёма и источник целевого ПДО. Подсказка следующего подхода объясняется отдельно по свежему рабочему факту, цели ПДО и замороженному шагу веса; она не меняет план в заголовке. Раскрытие пояснений не делает запросов, существующий `GET /api/sessions/{id}` не создаёт занятий или недель.

Целевой ПДО убран из редактора программы: лёгкая фаза назначает **4**, возвращение в обычную фазу после непропущенной лёгкой недели — **2,5**, обычная фаза — **2**. Возвращение действует на занятия этой недели, не только на первую тренировку. Две лёгкие недели подряд сохраняют цель **4**. Фактический ПДО нового подхода изначально пустой и обязателен для рабочего подхода; 0 означает записанный факт, неизвестный ПДО не подставляется из цели.

Новых маршрутов нет. Ответ элемента занятия дополнен nullable-полем `recommendation`: `version`, `rules_version`, `created_at`, `inputs`, `history`, причины `weight`/`reps`/`sets`/`rir`, исходный `calculated` и известные `manual_override`. В `next_set` добавлено `basis`: исходный подход, его вес/повторы/фактический ПДО, цель, разница и шаг. Числа и причины выдаёт один серверный расчёт; клиент не реализует свою формулу. Существующие поля целей и `action_label` сохранены.

`Exercise.rir_target` оставлен как устаревшее поле API/БД (`number | null`), не влияющее на назначение. Старый клиент может передать известное значение или NULL; отсутствие поля при обновлении сохраняет прежнее, допустимый 0 не превращается в 2. Новый клиент поле не отправляет. Снимки ПДО занятия и факта не меняются задним числом.

Добавочная миграция **6** добавляет только `session_exercises.recommendation_context_json TEXT NULL`. Объяснение создаётся одновременно с новым планом. Старым занятиям и вручную составленным демопланам не выдумываются входы: они показывают «Подробности расчёта не сохранены». Ручное изменение веса/повторов/числа подходов отмечается отдельно, исходный автоматический расчёт сохраняется; если исходный расчёт старого занятия неизвестен, `calculated` остаётся NULL. Вес ручной цели в пояснении совпадает с фактически сохранённой точностью БД.

Существующий явный перенос неначатого занятия пересчитывает автоматический план на выбранную дату и сохраняет отмеченные ручные цели; диапазон и шаг снимка согласуются с этим расчётом. Уже заменённое назначение по-прежнему запрещает перенос. Происхождение ручных целей, сделанных старыми версиями без отметки, восстановить нельзя; новая версия не объявляет их известными. Просмотр, изменение программы и исправление источника сами по себе не пересчитывают сохранённый план/объяснение. Изменение завершённых фактов через API не добавлено.

Сервер и клиент обновляются одной согласованной версией. Не чередуйте старый сервер и новый на одной базе: старый код не поддерживает обновление пояснений и отметок ручных целей. При интеграции параллельной ветки сохраняйте контракт миграции 6 и JSON версии 1; исходные идентичности `id`/`slot_id`/`history_id` не меняются. Перед изменением существующей базы нужны проверенные бэкап и восстановление. Тесты используют только свои SQLite-файлы и временные PostgreSQL-схемы.

Для полного прогона используйте команду выше с `--basetemp=.venv/pytest-stage2` и явно заданным URL тестовой PostgreSQL. Сценарии находятся в `test_recommendations.py` и `test_recommendation_migration.py`; прежние проверки истории также сохраняются. Предпросмотр ещё не созданного занятия, недельный прогноз, новая методика оборудования и календарные изменения в этап 2 не входят.

## Правила прогрессии

- При добавлении упражнения в день программы можно сразу создать новый вид: указать название, основную и вторичные мышцы и якорный признак. Можно также выбрать уже созданное упражнение из справочника. Старые упражнения необходимо связать со справочником: приложение не угадывает их мышечную принадлежность по названию.
- Для каждого дня задаются базовые подходы, диапазон повторений, стартовый вес и шаг веса. Движок ведёт прогрессию отдельно для каждого места упражнения в программе. Якорное упражнение сохраняйте в течение мезоцикла; вспомогательные можно заменить между блоками.
- На неделях накопления целевой RIR — 2, коридор 1–3. Базовый вес — округлённая к шагу медиана первых рабочих весов до трёх последних завершённых обычных занятий выбранной базы; для занятия без рабочих подходов берётся сохранённый плановый вес. Условия прибавки проверяются по последнему занятию: все назначенные рабочие подходы достигли верха диапазона и RIR каждого ≥ 1 — плюс шаг веса; одинаковые веса подходов не требуются. Иначе при известном RIR ≥ 1 предлагается округлённая медиана рабочих повторов плюс один, ограниченная обеими границами диапазона. Вес округляется к ближайшему кратному шагу, половина вверх; повторы и подходы используют округление половин к чётному. При недостаточном/неизвестном RIR — нижняя граница повторов с базовым весом. Новые рабочие подходы требуют явного ввода RIR с шагом 0,5. Разминка не входит в расчёт.
- Жёсткий подход — рабочий подход с RIR ≤ 3: основной мышце засчитывается 1, вторичной — 0,5. Пользователь может настроить недельный диапазон и предел для каждой мышцы. При хорошем восстановлении движок добавляет не более одного подхода на мышцу за неделю; отметка «тяжело/болит» останавливает рост.
- Разгрузка назначается по календарю или сигналам восстановления. Она планирует половину базовых подходов с округлением, минимум один на упражнение, недельный предел 8 на мышцу, RIR 4 и без повышения веса. При хорошем восстановлении плановую разгрузку можно перенести один раз на неделю. Ручная разгрузка выбирается на экране программы до создания занятий этой недели.
- На неделе возвращения после непропущенной разгрузки обычные занятия идут без повышения веса и с целевым RIR 2,5. Фаза и графики недельного объёма основаны на фактической дате занятия. e1RM для 2–10 повторений остаётся вспомогательной оценкой, а не основанием для прогрессии.

## Безопасность и границы первой версии

Сервер проверяет HMAC-подпись и срок действия Telegram `initData`, а каждую операцию с программой или тренировкой ограничивает владельцем по Telegram ID. Webhook проверяет секрет Telegram. Пароли и токены хранятся только в `.env` на сервере.

Рассылка работает одним экземпляром API; при масштабировании на несколько экземпляров задачу отправки нужно выделить в отдельный процесс с блокировками. Возможна повторная отправка при аварии между успешным ответом Telegram и записью факта отправки в БД. Результаты при этом не дублируются.
