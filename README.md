# Линия силы — Telegram бот и Mini App

Бот присылает план по расписанию. Мини-приложение позволяет вести подходы, настраивать программу и видеть прогресс. В разделе «Программа» можно задать тренировочный цикл от 2 до 30 дней, указать занятия и повторять одну тренировку в разных днях цикла. После трёх полностью завершённых циклов накопления следует лёгкий цикл той же длины. Пропущенное занятие задерживает продвижение цикла, а перенос сохраняет назначенную фазу и цели. Ориентиры объёма пересчитываются пропорционально длительности цикла. Программы, ещё не переведённые на циклы, продолжают прежнее недельное расписание.

При первом `/start` бот просит пол, имя и дату рождения; те же данные можно внести при первом открытии Mini App и позже изменить в разделе «Программа». Пол выбирает мужскую или женскую схему на карточке сегодняшней тренировки. Две SVG-фигуры показывают мышцы спереди и сзади: красный — основная мышца, оттенки синего — дополнительная нагрузка по запланированным подходам. Возраст и пол не участвуют в формуле прогрессии. Версия схемы БД — 9; миграция добавляет расписание циклов, не изменяя записанные результаты. Справочник мышц включает приводящие мышцы.

Единственный администратор — Telegram ID `5540948403`. У него в Mini App есть раздел «Админ»: список зарегистрированных пользователей, поиск по username или имени и редактирование выбранной программы и справочника упражнений. Для обычных пользователей раздел не показывается, а сервер отклоняет прямые запросы поиска и чужой программы. Username сохраняется после следующего `/start` или входа пользователя в Mini App; пользователи без username отображаются по имени или Telegram ID.

Справочник упражнений общий: администратор добавляет и редактирует движения, а все пользователи видят их и могут назначать в свои тренировки. Ранее созданные личные движения остаются доступны их владельцу, но редактировать справочник через Mini App может только администратор.

Порядок упражнений в тренировке меняется перетаскиванием за ручку слева от названия. На клавиатуре ручка принимает стрелки вверх и вниз. Перестановка сохраняет назначение и его историю; уже созданные тренировки остаются со своим снимком порядка.

Визуальные принципы Mini App и изученные референсы описаны в [DESIGN.md](DESIGN.md).
Задачи, реализованные функции и текущие ограничения собраны в [PROJECT_STATUS.md](PROJECT_STATUS.md).

При повторном открытии браузер может использовать кеш хешированных JS/CSS файлов в течение года; шрифт и схемы мышц кешируются на сутки. HTML проверяется при каждом входе, а персональные ответы API запрашиваются заново. Экран загрузки показывается сразу из HTML, ещё до запуска React. Главная ожидает профиль и план на сегодня; программа, завершения за текущий день и следующая неделя догружаются отдельно. Скорость первого ответа API всё ещё зависит от Vercel и базы данных.

## Что нужно для запуска

- Бот и токен от [@BotFather](https://t.me/BotFather).
- Домен с DNS-записью на VPS и открытыми портами 80/443.
- VPS с Docker Compose. Конфигурации 2 CPU / 4 ГБ достаточно для небольшого числа пользователей.

## Развёртывание

### Vercel Hobby (свежая база)

Корневой `vercel.json` развёртывает Vite и FastAPI как два Vercel Services в одном проекте. Для данных нужен отдельный PostgreSQL из Vercel Marketplace, например Neon на бесплатном плане. Создайте **новую пустую** базу и передайте её строку подключения как `DATABASE_URL`. При первом обращении API применит миграции до схемы 9. Справочники видов упражнений и мышечных групп заданы кодом; упражнения, программы, тренировки и демонстрационные данные не импортируются.

В переменных Production задайте `APP_ENV=production`, `BOT_TOKEN`, `DATABASE_URL`, `PUBLIC_URL=https://<домен-проекта>.vercel.app`, случайные `WEBHOOK_SECRET` и `CRON_SECRET`, `DEV_TELEGRAM_ID=0`, `REMINDERS_ENABLED=true`. Секреты храните только в настройках Vercel, не в Git. На Vercel API не регистрирует webhook и не запускает фоновый цикл при старте функции. После успешной проверки `/health` зарегистрируйте Telegram webhook на `PUBLIC_URL/telegram/webhook` с заголовком-секретом `WEBHOOK_SECRET`; затем задайте `PUBLIC_URL` в BotFather как адрес Mini App.

Напоминания вызываются Vercel Schedule через защищённый `POST /api/internal/reminders` каждые 15 минут. На Hobby каждый запуск может дополнительно задерживаться до 15 минут: от назначенного пользователем времени до отправки может пройти почти 30 минут. Сборка не требует Docker на Vercel; локальный Docker Compose остаётся для самостоятельного запуска и проверок.

### Docker Compose на VPS

1. Скопируйте `.env.example` в `.env`. Укажите `BOT_TOKEN`, `DOMAIN`, `PUBLIC_URL=https://<домен>`, `POSTGRES_PASSWORD` и случайный `WEBHOOK_SECRET`. В `DATABASE_URL` укажите тот же пароль. Для публичного сервера поставьте `APP_ENV=production`, удалите или обнулите `DEV_TELEGRAM_ID`.
2. Выполните `docker compose up -d --build`. Caddy автоматически получит HTTPS-сертификат. API создаст таблицы и зарегистрирует webhook.
3. В BotFather настройте Main Mini App или кнопку меню на `PUBLIC_URL`. Отправьте боту `/start`, затем откройте приложение и создайте программу.
4. Проверьте `https://<домен>/health`, отправку `/today`, вход через Telegram и тестовое уведомление в выбранный день и время.

При запуске API применяет версионированные добавочные миграции схемы (`backend/app/migrations.py`). Перед обновлением сохраните резервную копию. Старые подходы остаются в истории с неизвестным RIR и не входят в новую аналитику жёстких подходов. Контейнер `backup` кладёт ежедневные дампы в `./backups` и хранит их 30 дней. Для защиты от потери VPS переносите копии на другое устройство или в объектное хранилище.

## Локальная разработка

### Быстрый просмотр через Docker

В корне проекта выполните в PowerShell:

```powershell
.\scripts\local.ps1 preview
```

Скрипт создаст игнорируемый Git файл `.env.local` со случайными секретами, соберёт локальные контейнеры и откроет приложение на `http://localhost:8080`. В режиме `preview` используется отдельный тестовый Telegram ID `123456789`; никаких сообщений бот не отправляет. Локальная PostgreSQL хранится в отдельном Docker volume. Изменения исходного кода требуют повторного запуска `preview` для пересборки.

Для проверки внутри Telegram создайте **отдельного тестового бота** через BotFather, впишите его токен в `TELEGRAM_BOT_TOKEN` файла `.env.local` на своём компьютере и выполните:

```powershell
.\scripts\local.ps1 telegram
```

Скрипт отключит вход по тестовому ID, запустит временный HTTPS-туннель Cloudflare и зарегистрирует webhook. Он выведет адрес Mini App. Отправьте тестовому боту `/start` в личном чате: ответ и кнопка меню откроют Mini App. Настройка Main Mini App в BotFather для этого пути не обязательна. Временный адрес меняется при повторном запуске туннеля; тогда снова выполните команду `telegram`. API в Telegram-режиме проверяет подпись `initData`. Сам интерфейс доступен по ссылке туннеля, поэтому используйте тестового бота и тестовые данные.

Для наполнения графиков локального предпросмотра примерами выполните:

```powershell
docker compose --env-file .env.local -f compose.local.yaml exec -T api python -m app.demo_seed
```

Скрипт добавляет к тестовому пользователю три программы с пометкой «ДЕМО» и 24 завершённые тренировки за восемь недель. Две недели отмечены как разгрузочные. Повторный запуск не дублирует записи; существующие тренировки не изменяются. Скрипт работает только при `APP_ENV=development` и настроенном `DEV_TELEGRAM_ID`.

Проверить контейнеры: `.\scripts\local.ps1 status`. Остановить их и удалить только локальный webhook: `.\scripts\local.ps1 stop`. Данные PostgreSQL при остановке сохраняются.

### Личный Telegram-стенд без Docker (Windows)

На этом компьютере подготовлен отдельный launcher `scripts/telegram_test.py`, использующий существующие Python/PostgreSQL и официальный portable cloudflared. Production, основной бот, `.env`, `.env.local`, Docker и системные службы не используются. Каталог **`.venv/telegram-test` содержит постоянные данные теста**, а не только инструменты: не удаляйте его при очистке или пересоздании virtualenv.

Сначала в [@BotFather](https://t.me/BotFather) отправьте `/newbot`, задайте отображаемое имя (например, «Линия силы — тест») и свободный username. Для защиты launcher требует окончание **`_test_bot`**, например `line_sily_demo_test_bot`. BotFather выдаст токен; храните его только локально, не отправляйте в чат и не используйте токен основного бота. Main Mini App настраивать не требуется: после `/start` наш бот создаёт кнопку открытия.

Заполните только `.venv/telegram-test/bot.env` (файл уже создан и игнорируется Git):

```dotenv
TEST_BOT_USERNAME=ваш_username_без_@
TEST_BOT_TOKEN=вставьте_токен_локально_без_кавычек
```

Из корня `gymbot`:

```powershell
# Проверка формата файла, без обращения в Telegram:
.\.venv\Scripts\python.exe scripts/telegram_test.py check
# Реальный запуск: временный HTTPS-адрес и webhook только проверенного тестового бота:
.\.venv\Scripts\python.exe scripts/telegram_test.py start
# Состояние / остановка:
.\.venv\Scripts\python.exe scripts/telegram_test.py status
.\.venv\Scripts\python.exe scripts/telegram_test.py stop
```

Равнозначная оболочка — `.\scripts\telegram-test.ps1 check/start/status/stop`. Python-команды не требуют изменения ExecutionPolicy. При первом подключении отправьте своему тестовому боту `/start` в личном чате. Последующие `start` автоматически обновляют кнопку «Тренировки» у зарегистрированных личных чатов после проверки бота и webhook; сообщения не отправляются. Используйте эту кнопку меню для нового запуска Mini App: кнопки внутри старых сообщений могут содержать уже недействующий адрес. Закройте старое окно Mini App перед повторным открытием. Компьютер должен оставаться включённым; URL временный и доступен извне, данные API требуют действительную Telegram-подпись.

После завершения процессов стенд сам не запускается: снова выполните `start`. Автозагрузка Windows, службы и постоянный внешний адрес этим launcher не настраиваются. Чужие URL в меню не заменяются; для такого чата скрипт предложит отдельно использовать `/start`. Telegram может добавить завершающий `/` в URL кнопки — проверка учитывает эту нормализацию.

Запуск ожидает ответ `/health` через публичный HTTPS-адрес до 120 секунд: появление URL в журнале ещё не означает готовность туннеля. Для этого стенда используется HTTP/2/TCP, поскольку проверка текущей сети выявила недоступность QUIC/UDP. Только после готовности адреса устанавливается webhook. Если DNS Telegram ещё не видит новый hostname, выполняются до семи попыток с паузой пять секунд и проверкой владельца перед каждой; другие ошибки не повторяются. При недоступности туннеля стенд останавливается с сохранением данных. Менять системный DNS, firewall или токен для этого не требуется.

`start` сначала сверяет токен с указанным username, ID предыдущего сеанса и текущим webhook. Чужой/неизвестный webhook не заменяется. На `stop` удаляется только webhook того же бота, в точности совпадающий с адресом собственного туннеля; чужой URL сохраняется. Если удаление нельзя проверить из-за сети, приватная копия сеанса сохраняется для повторного `stop`; новый запуск блокируется до подтверждённой очистки. Автоматические напоминания отключены (`reminders_enabled=False`); ответы на ваши команды работают. В обычном запуске флаг по умолчанию True, прежнее поведение не меняется.

База: новый PGDATA `.venv/telegram-test/postgres/data`, собственная роль/пароль и отдельный loopback-порт. Синтетический кластер серверных тестов `.venv/pg17-data-runtime` не используется. Перед каждым запуском API создаётся приватный `pg_dump` в `backups`; остановка сохраняет базу, токен и копии. Секреты не передаются в командной строке и маскируются в логах. Settings передаются явно с `_env_file=None`, dev ID равен 0. Клиент собирается отдельно в `client-dist`, без чтения dotenv-файлов и наследования VITE-переменных.

`prepare` повторно готовит инструменты/кластер и собирает клиент; запущенный стенд сначала нужно остановить. Оно не запускает бота или туннель. Для служебной проверки есть `start --offline`: только loopback API/статика, пустой токен, вход без Telegram закрыт. После неё выполните `stop`. Режим не предназначен для записи тренировок через dev-пользователя.

При 502/503/504 и Cloudflare 530 клиент повторяет только GET-загрузки: не более пяти попыток с паузами 1 / 3 / 7 / 12 секунд. Суммарное ожидание между запросами — 23 секунды плюс время самих запросов; это позволяет переждать наблюдавшееся 20-секундное переподключение туннеля. Запросы записи, ошибки авторизации и прочие HTTP-ошибки не повторяются. Повтор GET `/sessions/today` использует существующую идемпотентность создания планов; это не превращает этот маршрут в read-only preview. Постоянный сбой остаётся видимой ошибкой. Повторы не устраняют сетевые обрывы; если 530 сохранилась, после восстановления соединения нажмите «Повторить загрузку». Незагруженная программа не отображается как ноль дней или форма создания; при неудачном обновлении уже загруженные дни и редактор сохраняются с отметкой времени последнего чтения.

На другом компьютере сначала нужны существующее `.venv`, зависимости backend/frontend и portable PostgreSQL 17 в `.venv/pg17/pgsql`; launcher не устанавливает службы или глобальные пакеты. Cloudflared закреплён на [официальном релизе 2026.10.7](https://github.com/cloudflare/cloudflared/releases/tag/2026.10.7) и проверяется SHA256 до выполнения. Собственный пустой конфиг/отсутствующий origin-cert и очищенное окружение не подхватывают пользовательские named tunnels/сертификаты.

### Запуск без Docker для разработки

Локальный фронтенд работает без Telegram, если `DEV_TELEGRAM_ID` в `.env` совпадает с `VITE_DEV_TELEGRAM_ID` при запуске Vite. Этот режим доступен только при `APP_ENV=development`.

1. Запустите PostgreSQL и задайте локальный `DATABASE_URL` либо используйте SQLite (`sqlite:///./workout.db`) для быстрой разработки.
2. В `backend` создайте окружение Python 3.12+, установите `pip install -r requirements.txt` и запустите `uvicorn app.main:app --reload --port 8000`.
3. В `frontend` установите зависимости через `npm install` и запустите `VITE_DEV_TELEGRAM_ID=<ваш ID> npm run dev` (в PowerShell: `$env:VITE_DEV_TELEGRAM_ID='<ваш ID>'; npm run dev`). Откройте `http://localhost:5173`.
4. Для тестов сервера: из `backend` запустите `pytest`.

### Сравнение независимых вариантов: база этапа 0

Общий исходный commit: `e49360fc1f2f2696ba6ba0e3ca506af0245224b3`. Каждый вариант использует собственную ветку, окружение и тестовую базу. Проверки этого этапа не запускают API lifespan, Telegram-бота, webhook или рассылку. Фактические результаты и известные падения перечислены в [PROJECT_STATUS.md](PROJECT_STATUS.md).

Из корня отдельного clone:

```powershell
New-Item -ItemType Directory -Path .venv/tmp -Force | Out-Null
$env:TEMP = (Resolve-Path .venv/tmp).Path
$env:TMP = $env:TEMP
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt -c backend/requirements-baseline.txt
$env:PYTEST_DISABLE_PLUGIN_AUTOLOAD = '1'
.\.venv\Scripts\python.exe -m pytest -c backend/pytest.ini backend/tests -q -m 'not history_regression' --basetemp=.venv/pytest-stage0
.\.venv\Scripts\python.exe -m pytest -c backend/pytest.ini backend/tests -q -m history_regression --basetemp=.venv/pytest-stage0
```

Временный каталог внутри игнорируемого `.venv` используется из-за отказа записи Python в системный TEMP внутри текущего Windows sandbox. Путь `.venv/pytest-stage0` зарезервирован для pytest и пересоздаётся при запуске; ручные данные в него не помещать.

`requirements-baseline.txt` фиксирует разрешённые существующим `requirements.txt` зависимости для сравнения на Windows / Python 3.14.5. Это отдельные ограничения тестовой базы; production-зависимости не изменены. На другой ОС могут добавиться платформенные зависимости исходного requirements. Фронтенд устанавливается существующим `pnpm install --frozen-lockfile` (pnpm 11.25.0) и проверяется `pnpm run build` из `frontend`; lockfile не пересоздавать.

Клиентские проверки транспорта и состояний загрузки: `node --test frontend/tests/*.test.mjs` из корня репозитория либо `pnpm test` из frontend. Используется уже имеющийся Node 24 с встроенными node:test и поддержкой TypeScript; новые зависимости не требуются. Проверки отрисовки используют React SSR и Vite с envDir:false, без открытия браузера, Telegram и реальных API-запросов. Они не заменяют отдельную проверку Mini App в Telegram.

Если глобальный pnpm недоступен, тот же инструмент можно установить только в игнорируемое окружение проекта. Этот путь использован в текущей Windows-проверке:

```powershell
npm install --prefix .venv/frontend-tools --no-save --ignore-scripts --package-lock=false --cache .venv/npm-cache pnpm@11.25.0
Push-Location frontend
node ../.venv/frontend-tools/node_modules/pnpm/bin/pnpm.cjs install --frozen-lockfile --store-dir ../.venv/pnpm-store
node ../.venv/frontend-tools/node_modules/pnpm/bin/pnpm.cjs run build
Pop-Location
```

Первая группа проверяет существующие сценарии, сохранность снимков и миграцию. Вторая содержит шесть приёмочных регрессий смешивания истории: на commit `57327b1` они падали без `xfail`, в итоговом прогоне этапа 1 прошли. Полный запуск без `-m` включает обе группы.

Общий helper `replace` в `tests/test_history.py` использует отдельный API замены. Он обновлён под согласованный контракт этапа 1; проверки пользовательского результата сохранены.

`tests/conftest.py` до импорта приложения принудительно задаёт development, пустой токен, отключённый dev-вход и служебный SQLite in-memory URL. Данные сценариев находятся во временных SQLite-файлах pytest. Календарные часы планирования, завершения, бота и аналитики устанавливаются на 26.10.2026 12:00 UTC и могут явно переводиться фикстурой `clock`. Синтетические завершения исходного набора используют дату сценария, поэтому порядок истории не зависит от скорости выполнения тестов.

Для проверки PostgreSQL нужен отдельный временный сервер. Не использовать рабочий DATABASE_URL. Пример, если Docker Engine уже доступен:

```powershell
docker run --detach --name gymbot-stage0-yourname --label gymbot.stage=stage0 --env POSTGRES_HOST_AUTH_METHOD=trust --env POSTGRES_USER=gymbot_test --env POSTGRES_DB=gymbot_test --publish 127.0.0.1:55443:5432 --mount type=tmpfs,destination=/var/lib/postgresql/data postgres:17-alpine
# После готовности pg_isready:
$env:GYMBOT_TEST_POSTGRES_URL = 'postgresql+psycopg://gymbot_test@127.0.0.1:55443/gymbot_test?connect_timeout=5'
.\.venv\Scripts\python.exe -m pytest -c backend/pytest.ini backend/tests/test_migrations_legacy.py -q --basetemp=.venv/pytest-stage0
```

Имя контейнера и свободный loopback-порт должны быть своими. Доступ без пароля допустим здесь только для одноразовых синтетических данных на loopback; контейнер не подключается к постоянному volume. Тест принимает только локальную БД с именем `gymbot_test`, создаёт собственную схему `gymbot_stage1_<uuid>` и удаляет только её. Проверяются исходные строки, связи, факты, тоннаж, неизвестные значения, доступность истории, повторное применение миграций 1–5 и восстановление синтетической копии. Без специального URL PostgreSQL-проверка получает явный `SKIPPED`. После проверки остановите и удалите только созданный вами тестовый контейнер; tmpfs при остановке теряется.

Для одновременного browser preview на одном компьютере нужны разные Compose project names, порты и volume. В `compose.local.yaml` закреплены общее имя и порт 8080, а `local.ps1 preview` может удалить ранее настроенный локальный webhook. Эти команды не являются изолированными по одному лишь расположению clone. На этапе 0 они не используются.

### Безопасная замена: этап 1

В программе есть отдельные действия «Изменить настройки» и «Заменить упражнение». Настройки сохраняют движение и базу результатов. Замена создаёт новое назначение и архивирует прежнее. Все созданные занятия сохраняют движение, цели и результаты; новое назначение применяется со следующего нового занятия. Отдельная замена на одно занятие в этот этап не входит.

При возвращении можно продолжить выбранную прежнюю базу или начать новую. Продолжение доступно только для того же `movement_id`, типа и места программы; одинаковые названия, разные места и дни не объединяются. Базы показывают дату, число занятий и последний собственный результат. Смешанная/неизвестная старая история сохранена, но не предлагается для продолжения автоматически. Для новой базы нужен явный старт; при продолжении старт подтверждается как запасной вариант, если нет подходящих обычных занятий. Ноль килограммов допустим при явном вводе; для временных типов нужны положительные минуты, автоматической прогрессии минут нет.

`Exercise.id` обозначает назначение, `slot_id` — постоянное место, `history_id` — базу результатов. Каждая замена получает новый `id`; старые назначения не активируются повторно. Сервер назначает эти идентификаторы; один слот имеет не более одного активного назначения. Перестановка меняет порядок, но не идентичности. Рекомендации и аналитика дополнительно проверяют движение/тип снимка, чтобы не смешивать старые записи, когда-то изменённые на месте. Новая база не удаляет факты, не обнуляет недельную нагрузку мышц и не переключает фазу. Формула веса и приоритет ПДО недели/возвращения сохранены.

| API | Контракт |
| --- | --- |
| `PUT /api/exercises/{id}` | Настройки того же движения; смена движения даёт `409`. |
| `GET /api/exercises/{id}/history-options?movement_id=…` | Только чтение доступных баз; не создаёт недели или занятия. |
| `POST /api/exercises/{id}/replace` | `{movement_id, history_mode: "new" / "resume", history_id: null / выбранный, settings}`. |

Для силового `settings` содержит все пять полей: `sets_count`, `medium_weight`, `weight_step`, `rep_min`, `rep_max`; для временного — только `duration_minutes`. Шаг веса должен помещаться в существующую точность БД: минимум 0,01 кг, до двух десятичных знаков; это проверка хранения, не новая методика оборудования. Ответ замены: `{exercise, history_mode, effective_from: "next_new_session", preserved_sessions_count}`. Повтор на старый `id` даёт `409` без дубля; после потерянного ответа следует обновить программу и сверить результат. Чужие идентификаторы дают `404`, некорректные параметры — `422`, несовместимая база — `409`.

Тип уже использованного движения в справочнике фиксирован; для другого типа создают другое движение. Исправление названия возможно и не меняет старые снимки. Новое поле `Movement.is_used` позволяет объяснить это в редакторе.

`SessionExercise.weight_step` теперь снимок, а не ссылка на текущую настройку. Для старых занятий он остаётся `NULL`: ручной ввод веса доступен, зависимые кнопки и подсказка следующего подхода отключены с пояснением. Силовые серии прогресса имеют непрозрачный `id`, отдельные `history_id`/`slot_id`/`movement_id` и понятный `label`; `id` серии не является идентификатором назначения для записи в API.

Перенос занятия с архивным/заменённым назначением временно запрещён (`409`); запись и завершение доступны. Запрос той же даты не меняет занятие. Политика пересчёта при переносе относится к отдельному календарному этапу. Лимит журнала 100 последних занятий на этом этапе не расширяется; сохранённые записи и их идентификаторы не удаляются.

Добавочная миграция **5** устанавливает известные `slot_id = id`, `history_id = id`, добавляет nullable-шаг снимка и уникальный индекс активного слота. Исторические факты, движения и неизвестные значения не восстанавливаются догадками. До будущего изменения существующей базы нужна проверенная резервная копия. Совместимость схемы добавочная, но старый код не понимает продолжение общей базы: сервер и клиент обновляются одной согласованной версией, а откат проверяется восстановлением копии. Два независимых варианта используют этот же контракт миграции 5 и свои базы; отдельную конфликтующую миграцию с тем же номером не выпускать.

Полный серверный прогон с PostgreSQL:

```powershell
$env:GYMBOT_TEST_POSTGRES_URL = 'postgresql+psycopg://gymbot_test@127.0.0.1:55443/gymbot_test?connect_timeout=5'
$env:PYTEST_DISABLE_PLUGIN_AUTOLOAD = '1'
.\.venv\Scripts\python.exe -m pytest -c backend/pytest.ini backend/tests -q --basetemp=.venv/pytest-stage1
```

В Windows-проверке использован официальный portable PostgreSQL **17.11** по ссылке со [страницы PostgreSQL для Windows](https://www.postgresql.org/download/windows/) на [EDB binaries](https://www.enterprisedb.com/download-postgresql-binaries). Он находится только в игнорируемом `.venv/pg17`, без службы, реестра или изменения Docker. Локальный сервер: `.venv/pg17/pgsql/bin/pg_ctl.exe -D .venv/pg17-data-runtime -l .venv/pg17-data-runtime/server.log -o "-h 127.0.0.1 -p 55443" -w start`; остановка: тот же `pg_ctl` с `-m fast -w stop`. Команды относятся только к созданному тестовому кластеру с loopback-конфигурацией. На другом компьютере сначала подготовьте собственный пустой кластер; не подставляйте рабочий PGDATA. Результаты проверок и реальные ограничения — в PROJECT_STATUS.md.

### Объяснение плана и ПДО: этап 2

В созданной силовой тренировке и истории раскрывается «Почему такой план?». Это сохранённые входы и результат расчёта: до трёх собственных обычных занятий, рабочие факты, медиана и округление веса, причина повторов/подходов, пределы недельного объёма и источник целевого ПДО. Подсказка следующего подхода объясняется отдельно по свежему рабочему факту, цели ПДО и замороженному шагу веса; она не меняет план в заголовке. Раскрытие пояснений не делает запросов, существующий `GET /api/sessions/{id}` не создаёт занятий или недель.

Целевой ПДО убран из редактора программы: лёгкая фаза назначает **4**, возвращение в обычную фазу после непропущенной лёгкой недели — **2,5**, обычная фаза — **2**. Возвращение действует на занятия этой недели, не только на первую тренировку. Две лёгкие недели подряд сохраняют цель **4**. Фактический ПДО нового подхода изначально пустой и обязателен для рабочего подхода; 0 означает записанный факт, неизвестный ПДО не подставляется из цели.

Новых маршрутов нет. Ответ элемента занятия дополнен nullable-полем `recommendation`: `version`, `rules_version`, `created_at`, `inputs`, `history`, причины `weight`/`reps`/`sets`/`rir`, исходный `calculated` и известные `manual_override`. В `next_set` добавлено `basis`: исходный подход, его вес/повторы/фактический ПДО, цель, разница и шаг. Числа и причины выдаёт один серверный расчёт; клиент не реализует свою формулу. Существующие поля целей и `action_label` сохранены.

`Exercise.rir_target` оставлен как устаревшее поле API/БД (`number | null`), не влияющее на назначение. Старый клиент может передать известное значение или NULL; отсутствие поля при обновлении сохраняет прежнее, допустимый 0 не превращается в 2. Новый клиент поле не отправляет. Снимки ПДО занятия и факта не меняются задним числом.

Добавочная миграция **6** добавляет только `session_exercises.recommendation_context_json TEXT NULL`. Объяснение создаётся одновременно с новым планом. Старым занятиям и вручную составленным демопланам не выдумываются входы: они показывают «Подробности расчёта не сохранены». Ручное изменение веса/повторов/числа подходов отмечается отдельно, исходный автоматический расчёт сохраняется; если исходный расчёт старого занятия неизвестен, `calculated` остаётся NULL. Вес ручной цели в пояснении совпадает с фактически сохранённой точностью БД.

Существующий явный перенос неначатого занятия пересчитывает автоматический план на выбранную дату и сохраняет отмеченные ручные цели; диапазон и шаг снимка согласуются с этим расчётом. Уже заменённое назначение по-прежнему запрещает перенос. Происхождение ручных целей, сделанных старыми версиями без отметки, восстановить нельзя; новая версия не объявляет их известными. Просмотр, изменение программы и исправление источника сами по себе не пересчитывают сохранённый план/объяснение. Изменение завершённых фактов через API не добавлено.

Сервер и клиент обновляются одной согласованной версией. Не чередуйте старый сервер и новый на одной базе: старый код не поддерживает обновление пояснений и отметок ручных целей. При интеграции параллельной ветки сохраняйте контракт миграции 6 и JSON версии 1; исходные идентичности `id`/`slot_id`/`history_id` не меняются. Перед изменением существующей базы нужны проверенные бэкап и восстановление. Тесты используют только свои SQLite-файлы и временные PostgreSQL-схемы.

Для полного прогона используйте команду выше с `--basetemp=.venv/pytest-stage2` и явно заданным URL тестовой PostgreSQL. Сценарии находятся в `test_recommendations.py` и `test_recommendation_migration.py`; прежние проверки истории также сохраняются. Предпросмотр ещё не созданного занятия, недельный прогноз, новая методика оборудования и календарные изменения в этап 2 не входят.

### API предпросмотра нового занятия

```http
GET /api/templates/{template_id}/preview?on_date=YYYY-MM-DD
```

Дата обязательна: от сегодня до воскресенья следующей недели включительно по `User.timezone`. Она может отличаться от дня расписания, как и существующий ручной запуск. API оценивает одно новое занятие на эту дату по текущим данным; промежуточные тренировки и несохранённые календарные недели не симулируются. Расчёт предварительный: изменение фактов, программы, исключений или состояния недель может изменить результат настоящего создания.

| Состояние HTTP 200 | Ответ |
| --- | --- |
| `ready` | Цели нового занятия и объяснение без сохранения. |
| `existing` | Есть незавершённое занятие этого дня программы либо занятие на указанную дату. Только `existing_session: {id, scheduled_date, status}`; цели не пересчитываются. Сохранённый план читается обычным `GET /api/sessions/{id}`. |
| `blocked` | `blocking_reasons` с кодом и объяснением: `vacation`, `empty_program` или `needs_configuration`. Цели не выдумываются. |

Общие поля: `template_id`, `on_date`, `timezone`, `computed_at`, `provisional: true`, `persisted: false`, `week`, `exercises`, `existing_session`, `blocking_reasons`. `week` содержит дату начала, номер, фазу, причину разгрузки, флаги и `source: saved / calculated`; фиктивного `week_id` нет. Для новой недели решение вычисляется в памяти, включая влияние пропущенной разгрузки, без изменения прежней отметки. Существующая неделя использует сохранённые параметры, как при создании. Явный отпуск имеет приоритет над старой несовместимой записью фазы: preview возвращает blocked/vacation без исправления сохранённых строк.

У упражнений возвращаются реальные `exercise_id`, `slot_id`, `history_id`, `movement_id`, название, тип, порядок и цели. Силовое получает вес, подходы, повторы, ПДО и временное `recommendation` версии 1 по правилам этапа 2. Временное упражнение получает минуты; вес/подходы/повторы/ПДО имеют NULL как неприменимые поля. Новых идентификаторов занятий, циклов и снимков нет; объяснение не записывается в `recommendation_context_json`.

Неполная привязка движения в другом активном собственном дне блокирует силовой расчёт, если нужен общий бюджет объёма. Для занятия только на время другой день не влияет на минуты и не блокирует предпросмотр. Самостоятельного создания движения, угадывания его типа/мышц или объединения истории нет.

Telegram HMAC, срок действия и ограниченный dev-вход проверяются существующей общей функцией. Чужой/удалённый/неизвестный день и подписанный неизвестный пользователь дают `404` без регистрации; отсутствующая/недействительная подпись — `401`, пропущенная/некорректная/недопустимая дата — `422`. Успешный ответ имеет `Cache-Control: no-store`.

Предпросмотр использует PostgreSQL `REPEATABLE READ` + `READ ONLY` либо SQLite `query_only` и явную читающую транзакцию. Autoflush отключён; ORM-сущности не изменяются. Завершение читающей транзакции не является сохранением пробного плана с последующим откатом. После запроса и ошибки режим соединения восстанавливается для обычных операций. Одинаковые входы и дата дают одинаковые цели/причины; `computed_at` отражает момент чтения. Для равного времени завершения истории используется стабильный порядок по существующему ID.

Фрагмент синтетического примера из `test_preview.py`: дата 26.10.2026 управляется тестовыми часами, собственная программа имеет старт 60 кг, 3 подхода, диапазон 6–12 и шаг 2,5 кг, истории нет. Ответ: `state: ready`, `week.source: calculated`, **60 кг · 3 × 6 · ПДО 2**, `recommendation.history: []`. Недели, циклы, занятия, снимки и факты после просмотра не появляются. Настоящее создание проверяется отдельным действием только после полной сверки неизменности БД.

Проверки: общий серверный запуск из предыдущего раздела с `--basetemp=.venv/pytest-preview`; отдельно `backend/tests/test_preview.py`. Они используют собственные SQLite-файлы и PostgreSQL-схемы, запрещают SQL DML/DDL и вызовы `Session.flush/commit`, сверяют все таблицы вместе с `schema_versions`, проверяют реальную защиту чтения и отсутствие утечки режима в пул соединений. Миграция не нужна: схема остаётся **6**, контракт объяснения версии 1 сохранён. API добавочный; общие функции расчёта для записи и чтения интегрируются вместе.

Интерфейс в этом шаге не меняется. Текущий `App.refresh()` вызывает `/api/sessions/today`, который создаёт занятия; подключение нового GET через этот общий refresh не даст читающий сценарий. Отдельный путь загрузки интерфейса согласуется позже. Production, webhook, публикация и слияние этим этапом не разрешаются.

## Правила прогрессии

- При добавлении упражнения в день программы можно сразу создать новый вид: указать название, основную и вторичные мышцы и якорный признак. Можно также выбрать уже созданное упражнение из справочника. Старые упражнения необходимо связать со справочником: приложение не угадывает их мышечную принадлежность по названию.
- Для каждого дня задаются базовые подходы, диапазон повторений, стартовый вес и шаг веса. Движок ведёт прогрессию отдельно для каждого места упражнения в программе. Якорное упражнение сохраняйте в течение мезоцикла; вспомогательные можно заменить между блоками.
- На неделях накопления целевой RIR — 2, коридор 1–3. Базовый вес — округлённая к шагу медиана первых рабочих весов до трёх последних завершённых обычных занятий выбранной базы; для занятия без рабочих подходов берётся сохранённый плановый вес. Условия прибавки проверяются по последнему занятию: все назначенные рабочие подходы достигли верха диапазона и RIR каждого ≥ 1 — плюс шаг веса; одинаковые веса подходов не требуются. Иначе при известном RIR ≥ 1 предлагается округлённая медиана рабочих повторов плюс один, ограниченная обеими границами диапазона. Вес округляется к ближайшему кратному шагу, половина вверх; повторы и подходы используют округление половин к чётному. При недостаточном/неизвестном RIR — нижняя граница повторов с базовым весом. Новые рабочие подходы требуют явного ввода RIR с шагом 0,5. Разминка не входит в расчёт.
- Жёсткий подход — рабочий подход с RIR ≤ 3: основной мышце засчитывается 1, вторичной — 0,5. Пользователь может настроить недельный диапазон и предел для каждой мышцы. При хорошем восстановлении движок добавляет не более одного подхода на мышцу за неделю; отметка «тяжело/болит» останавливает рост.
- Разгрузка назначается по календарю или сигналам восстановления. Она планирует половину базовых подходов с округлением, минимум один на упражнение, недельный предел 8 на мышцу, RIR 4 и без повышения веса. При хорошем восстановлении плановую разгрузку можно перенести один раз на неделю. Ручная разгрузка выбирается в меню «Следующая неделя» до создания занятий выбранной недели. Явный отпуск действует до отмены или замены: старый API ручной разгрузки не может его обойти; перенос, создание, завершение и preview учитывают отпуск даже при старой несовместимой записи фазы.
- На неделе возвращения после непропущенной разгрузки обычные занятия идут без повышения веса и с целевым RIR 2,5. При завершении на другой неделе исходная фаза и week_id плана сохраняются; графики недельной нагрузки используют фактическую дату. Ранее записанные строки не исправляются догадками. e1RM для 2–10 повторений остаётся вспомогательной оценкой, а не основанием для прогрессии.

### Общий свод и совместимость после аудита 08.11.2026

`GET /api/progress` дополнен массивом `weekly_summary`: те же недельные метрики, но каждый рабочий подход учитывается один раз. `weeks` сохраняет прежнюю мышечную атрибуцию 1/0,5. Общий тоннаж включает известные силовые факты старых записей даже без мышечной разметки/RIR; разминка, пропуски и временные упражнения исключены. Неизвестный RIR не становится нулём: `avg_rir` — по известным фактам или NULL, `rir_known_sets`/`rir_unknown_sets` показывают покрытие. Общего целевого коридора мышц нет (`target_low`/`target_high` — NULL). Неизвестная старая фаза остаётся `unknown`; смешанная неделя без календарной записи — `mixed`. Для старых занятий без фактической даты сохраняется существующая привязка графика к плановой дате; история явно отличает её от факта.

Новые поля добавочные, схема БД остаётся **6**. Старый клиент игнорирует `weekly_summary`; новый с прежним сервером предлагает выбрать мышцу вместо неверного пересчёта общего свода. Для новых завершений week_id/phase сохраняют план; прежние строки не переписываются. Переносить сервер, типы и новые регрессии согласованным пакетом. Неизвестное время завершения сортируется одинаково на SQLite/PostgreSQL; известные последние занятия имеют приоритет.

Редакторы защищены от двойного отправления; изменения одной тренировки выполняются последовательно. После ошибки ручной черновик сохраняется; новый совет не перезаписывает введённые вес/повторы. Запрос записи не повторяется автоматически. Если сервер подтвердил действие, а последующее чтение не прошло, сообщение предлагает обновить экран вместо повторного сохранения. Ошибка загрузки справочника отделена от пустого справочника. Бот работает с личными планами только в личном чате; сохранённые групповые/чужие chat_id не используются для напоминаний.

## Безопасность и границы первой версии

Сервер проверяет HMAC-подпись и срок действия Telegram `initData`, а каждую операцию с программой или тренировкой ограничивает владельцем по Telegram ID. Webhook проверяет секрет Telegram. Пароли и токены хранятся только в `.env` на сервере.

При проверке HMAC по токену бота из строки исключается только `hash`; поле `signature`, если оно присутствует, входит в расчёт наравне с остальными полями. Исключать одновременно `hash` и `signature` требуется только для отдельного протокола Ed25519 third-party validation, который приложение не использует. Правило сверено с [документацией Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app); новые HTTP-фикстуры включают `signature` и `query_id`, а `test_telegram_auth.py` также сохраняет проверку старого формата без `signature`.

Рассылка работает одним экземпляром API; при масштабировании на несколько экземпляров задачу отправки нужно выделить в отдельный процесс с блокировками. Возможна повторная отправка при аварии между успешным ответом Telegram и записью факта отправки в БД. Результаты при этом не дублируются.
