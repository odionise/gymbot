# Линия силы — Telegram бот и Mini App

Бот присылает план по расписанию. Мини-приложение позволяет вести подходы, настраивать программу и видеть прогресс. План строится по четырёхнедельным мезоциклам: три недели накопления и неделя разгрузки.

Визуальные принципы Mini App и изученные референсы описаны в [DESIGN.md](DESIGN.md).
Задачи, реализованные функции и текущие ограничения собраны в [PROJECT_STATUS.md](PROJECT_STATUS.md).

## Что нужно для запуска

- Бот и токен от [@BotFather](https://t.me/BotFather).
- Домен с DNS-записью на VPS и открытыми портами 80/443.
- VPS с Docker Compose. Конфигурации 2 CPU / 4 ГБ достаточно для небольшого числа пользователей.

## Развёртывание

1. Скопируйте `.env.example` в `.env`. Укажите `BOT_TOKEN`, `DOMAIN`, `PUBLIC_URL=https://<домен>`, `POSTGRES_PASSWORD` и случайный `WEBHOOK_SECRET`. В `DATABASE_URL` укажите тот же пароль. Для публичного сервера поставьте `APP_ENV=production`, удалите или обнулите `DEV_TELEGRAM_ID`.
2. Выполните `docker compose up -d --build`. Caddy автоматически получит HTTPS-сертификат. API создаст таблицы и зарегистрирует webhook.
3. В BotFather настройте Main Mini App или кнопку меню на `PUBLIC_URL`. Отправьте боту `/start`, затем откройте приложение и создайте программу.
4. Проверьте `https://<домен>/health`, отправку `/today`, вход через Telegram и тестовое уведомление в выбранный день и время.

При запуске API применяет версионированные добавочные миграции схемы (`backend/app/migrations.py`). Перед обновлением сохраните резервную копию. Старые подходы остаются в истории с неизвестным RIR и не входят в новую аналитику жёстких подходов. Контейнер `backup` кладёт ежедневные дампы в `./backups` и хранит их 30 дней. Для защиты от потери VPS переносите копии на другое устройство или в объектное хранилище.

## Локальная разработка

### Быстрый просмотр через Docker

В корне проекта выполните в PowerShell:

```powershell
.\scripts\local.ps1 preview
```

Скрипт создаст игнорируемый Git файл `.env.local` со случайными секретами, соберёт локальные контейнеры и откроет приложение на `http://localhost:8080`. В режиме `preview` используется отдельный тестовый Telegram ID `123456789`; никаких сообщений бот не отправляет. Локальная PostgreSQL хранится в отдельном Docker volume. Изменения исходного кода требуют повторного запуска `preview` для пересборки.

Для проверки внутри Telegram создайте **отдельного тестового бота** через BotFather, впишите его токен в `TELEGRAM_BOT_TOKEN` файла `.env.local` на своём компьютере и выполните:

```powershell
.\scripts\local.ps1 telegram
```

Скрипт отключит вход по тестовому ID, запустит временный HTTPS-туннель Cloudflare и зарегистрирует webhook. Он выведет адрес Mini App. Отправьте тестовому боту `/start` в личном чате: ответ и кнопка меню откроют Mini App. Настройка Main Mini App в BotFather для этого пути не обязательна. Временный адрес меняется при повторном запуске туннеля; тогда снова выполните команду `telegram`. API в Telegram-режиме проверяет подпись `initData`. Сам интерфейс доступен по ссылке туннеля, поэтому используйте тестового бота и тестовые данные.

Для наполнения графиков локального предпросмотра примерами выполните:

```powershell
docker compose --env-file .env.local -f compose.local.yaml exec -T api python -m app.demo_seed
```

Скрипт добавляет к тестовому пользователю три программы с пометкой «ДЕМО» и 24 завершённые тренировки за восемь недель. Две недели отмечены как разгрузочные. Повторный запуск не дублирует записи; существующие тренировки не изменяются. Скрипт работает только при `APP_ENV=development` и настроенном `DEV_TELEGRAM_ID`.

Проверить контейнеры: `.\scripts\local.ps1 status`. Остановить их и удалить только локальный webhook: `.\scripts\local.ps1 stop`. Данные PostgreSQL при остановке сохраняются.

### Запуск без Docker

Локальный фронтенд работает без Telegram, если `DEV_TELEGRAM_ID` в `.env` совпадает с `VITE_DEV_TELEGRAM_ID` при запуске Vite. Этот режим доступен только при `APP_ENV=development`.

1. Запустите PostgreSQL и задайте локальный `DATABASE_URL` либо используйте SQLite (`sqlite:///./workout.db`) для быстрой разработки.
2. В `backend` создайте окружение Python 3.12+, установите `pip install -r requirements.txt` и запустите `uvicorn app.main:app --reload --port 8000`.
3. В `frontend` установите зависимости через `npm install` и запустите `VITE_DEV_TELEGRAM_ID=<ваш ID> npm run dev` (в PowerShell: `$env:VITE_DEV_TELEGRAM_ID='<ваш ID>'; npm run dev`). Откройте `http://localhost:5173`.
4. Для тестов сервера: из `backend` запустите `pytest`.

### Сравнение независимых вариантов: база этапа 0

Общий исходный commit: `e49360fc1f2f2696ba6ba0e3ca506af0245224b3`. Каждый вариант использует собственную ветку, окружение и тестовую базу. Проверки этого этапа не запускают API lifespan, Telegram-бота, webhook или рассылку. Фактические результаты и известные падения перечислены в [PROJECT_STATUS.md](PROJECT_STATUS.md).

Из корня отдельного clone:

```powershell
New-Item -ItemType Directory -Path .venv/tmp -Force | Out-Null
$env:TEMP = (Resolve-Path .venv/tmp).Path
$env:TMP = $env:TEMP
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt -c backend/requirements-baseline.txt
$env:PYTEST_DISABLE_PLUGIN_AUTOLOAD = '1'
.\.venv\Scripts\python.exe -m pytest -c backend/pytest.ini backend/tests -q -m 'not history_regression' --basetemp=.venv/pytest-stage0
.\.venv\Scripts\python.exe -m pytest -c backend/pytest.ini backend/tests -q -m history_regression --basetemp=.venv/pytest-stage0
```

Временный каталог внутри игнорируемого `.venv` используется из-за отказа записи Python в системный TEMP внутри текущего Windows sandbox. Путь `.venv/pytest-stage0` зарезервирован для pytest и пересоздаётся при запуске; ручные данные в него не помещать.

`requirements-baseline.txt` фиксирует разрешённые существующим `requirements.txt` зависимости для сравнения на Windows / Python 3.14.5. Это отдельные ограничения тестовой базы; production-зависимости не изменены. На другой ОС могут добавиться платформенные зависимости исходного requirements. Фронтенд устанавливается существующим `pnpm install --frozen-lockfile` (pnpm 11.25.0) и проверяется `pnpm run build` из `frontend`; lockfile не пересоздавать.

Если глобальный pnpm недоступен, тот же инструмент можно установить только в игнорируемое окружение проекта. Этот путь использован в текущей Windows-проверке:

```powershell
npm install --prefix .venv/frontend-tools --no-save --ignore-scripts --package-lock=false --cache .venv/npm-cache pnpm@11.25.0
Push-Location frontend
node ../.venv/frontend-tools/node_modules/pnpm/bin/pnpm.cjs install --frozen-lockfile --store-dir ../.venv/pnpm-store
node ../.venv/frontend-tools/node_modules/pnpm/bin/pnpm.cjs run build
Pop-Location
```

Первая группа проверяет существующие сценарии, сохранность снимков и миграцию. Вторая содержит шесть обычных падающих регрессий смешивания истории: это воспроизведённые дефекты, а не `xfail` и не успешная проверка. Полный запуск без `-m` включает обе группы и пока завершается с ошибкой.

Общий helper `replace` в `tests/test_history.py` воспроизводит текущий PUT назначения. Перед изменением API замены согласуйте контракт двух вариантов и адаптацию helper, сохранив проверки пользовательского результата.

`tests/conftest.py` до импорта приложения принудительно задаёт development, пустой токен, отключённый dev-вход и служебный SQLite in-memory URL. Данные сценариев находятся во временных SQLite-файлах pytest. Календарные часы планирования, завершения, бота и аналитики устанавливаются на 26.10.2026 12:00 UTC и могут явно переводиться фикстурой `clock`. Синтетические завершения исходного набора используют дату сценария, поэтому порядок истории не зависит от скорости выполнения тестов.

Для проверки PostgreSQL нужен отдельный временный сервер. Не использовать рабочий DATABASE_URL. Пример, если Docker Engine уже доступен:

```powershell
docker run --detach --name gymbot-stage0-yourname --label gymbot.stage=stage0 --env POSTGRES_HOST_AUTH_METHOD=trust --env POSTGRES_USER=gymbot_test --env POSTGRES_DB=gymbot_test --publish 127.0.0.1:55443:5432 --mount type=tmpfs,destination=/var/lib/postgresql/data postgres:17-alpine
# После готовности pg_isready:
$env:GYMBOT_TEST_POSTGRES_URL = 'postgresql+psycopg://gymbot_test@127.0.0.1:55443/gymbot_test'
.\.venv\Scripts\python.exe -m pytest -c backend/pytest.ini backend/tests/test_migrations_legacy.py -q --basetemp=.venv/pytest-stage0
```

Имя контейнера и свободный loopback-порт должны быть своими. Доступ без пароля допустим здесь только для одноразовых синтетических данных на loopback; контейнер не подключается к постоянному volume. Тест принимает только локальную БД с именем `gymbot_test`, создаёт собственную схему `gymbot_stage0_<uuid>` и удаляет только её. Проверяются все исходные строки, ключевые связи, факты и тоннаж, неизвестные значения, доступность старой истории и повторное применение миграций 1–4. Без специального URL PostgreSQL-проверка получает явный `SKIPPED`. После проверки остановите и удалите только созданный вами тестовый контейнер; tmpfs при остановке теряется.

Для одновременного browser preview на одном компьютере нужны разные Compose project names, порты и volume. В `compose.local.yaml` закреплены общее имя и порт 8080, а `local.ps1 preview` может удалить ранее настроенный локальный webhook. Эти команды не являются изолированными по одному лишь расположению clone. На этапе 0 они не используются.

## Правила прогрессии

- При добавлении упражнения в день программы можно сразу создать новый вид: указать название, основную и вторичные мышцы и якорный признак. Можно также выбрать уже созданное упражнение из справочника. Старые упражнения необходимо связать со справочником: приложение не угадывает их мышечную принадлежность по названию.
- Для каждого дня задаются базовые подходы, диапазон повторений, стартовый вес и шаг веса. Движок ведёт прогрессию отдельно для каждого места упражнения в программе. Якорное упражнение сохраняйте в течение мезоцикла; вспомогательные можно заменить между блоками.
- На неделях накопления целевой RIR — 2, коридор 1–3. После достижения верхней границы во всех рабочих подходах при допустимом RIR вес увеличивается на шаг; иначе цель повторений растёт на одно. Новые рабочие подходы требуют ввода RIR с шагом 0,5. Разминка не входит в недельный объём.
- Жёсткий подход — рабочий подход с RIR ≤ 3: основной мышце засчитывается 1, вторичной — 0,5. Пользователь может настроить недельный диапазон и предел для каждой мышцы. При хорошем восстановлении движок добавляет не более одного подхода на мышцу за неделю; отметка «тяжело/болит» останавливает рост.
- Разгрузка назначается по календарю или сигналам восстановления. Она планирует около половины рабочих подходов, ориентир 5–8 на мышцу, с RIR 4 и без повышения веса. При хорошем восстановлении плановую разгрузку можно перенести один раз на неделю. Ручная разгрузка выбирается на экране программы до создания занятий этой недели.
- Первое занятие после разгрузки идёт без повышения веса и с мягким целевым RIR. Фаза и графики недельного объёма основаны на фактической дате занятия. e1RM для 2–10 повторений остаётся вспомогательной оценкой, а не основанием для прогрессии.

## Безопасность и границы первой версии

Сервер проверяет HMAC-подпись и срок действия Telegram `initData`, а каждую операцию с программой или тренировкой ограничивает владельцем по Telegram ID. Webhook проверяет секрет Telegram. Пароли и токены хранятся только в `.env` на сервере.

Рассылка работает одним экземпляром API; при масштабировании на несколько экземпляров задачу отправки нужно выделить в отдельный процесс с блокировками. Возможна повторная отправка при аварии между успешным ответом Telegram и записью факта отправки в БД. Результаты при этом не дублируются.
