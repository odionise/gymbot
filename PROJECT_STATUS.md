# Линия силы — состояние проекта

Актуально на 1 ноября 2026 года. Этап 0, ветка `codex/gymbot-baseline`, исходная база `e49360fc1f2f2696ba6ba0e3ca506af0245224b3`.

## Что реализовано по коду

- Редактор дней тренировок и справочник упражнений с подробными мышцами, вторичной нагрузкой и якорным упражнением. Упражнение можно добавить в несколько дней; прогрессия для каждого места считается отдельно.
- Четырёхнедельный мезоцикл: три недели накопления и разгрузка. Учитываются ранняя и ручная разгрузка, однократный перенос плановой, пропущенная разгрузка и мягкое возвращение после неё.
- Двойная прогрессия по фактическим рабочим подходам и ПДО (повторы до отказа); подсказка по весу и повторам следующего подхода. Разминочные подходы записываются отдельно.
- Недельная аналитика по подробным мышцам: прямые и косвенные жёсткие подходы, рабочие подходы, тоннаж, средний ПДО, сопоставимые повторы и сигналы. Разгрузка выделена на графиках.
- На главной есть краткая справка. В записи подхода вес, повторы и ПДО меняются вводом или стрелками. Чекбокс якорного упражнения имеет компактный размер.
- Пользователь задаёт предел подходов и отдельные цели по мышцам; отметка «тяжело/болит» влияет на рост объёма и перенос разгрузки.
- API сохраняет историю старого цикла. Для старых подходов RIR неизвестен, и они не влияют на новые сигналы восстановления. Добавочные миграции схемы выполняются при запуске API.
- Бот отправляет фазу, цели и причину рекомендации. Сохранились проверка подписи Telegram, разделение пользователей и локальный просмотр.
- Для просмотра графиков в локальном предпросмотре есть повторяемое заполнение демоданными (`python -m app.demo_seed`): три программы, 24 завершённые тренировки, два мезоцикла с разгрузкой.

## Проверки

- Исходные 15 серверных тестов на неизменённом продукте: **15 passed**. Это новый прогон, отдельно от старого отчёта о 12 тестах.
- Итоговый набор с управляемым временем: **26 passed, 6 failed, 1 skipped**. Шесть падений — явно помеченные `history_regression`, без `xfail`; они фиксируют желаемую изоляцию истории, которой в продукте пока нет. Остальные сценарии проходят.
- Пройдены сохранение снимков запланированного, начатого и завершённого занятия после изменения назначения и справочника; доступность истории после удаления назначения; приоритет ПДО недели и возвращения; граница календарной недели в трёх часовых поясах. Это функциональные вызовы на временной SQLite, не HTTP-проверка или работа в Telegram.
- SQLite: полный синтетический граф старой схемы из семи таблиц мигрирован до версии 4 и проверен после повторного применения. Исходные строки, ключевые связи, два фактических подхода и тоннаж 875 сохранены; неизвестные ПДО, движение и фактическая дата остались `NULL`; старая история доступна через функцию API.
- PostgreSQL-проверка подготовлена с отдельной временной схемой, но **не выполнена**. Docker Desktop 4.76.0 не смог запустить Engine: ошибка инициализации Inference manager / локального сокета `dockerInference`. Это ограничение среды; проверка получает `SKIPPED`, оно не подтверждает совместимость миграций с PostgreSQL. Восстановление Docker за пределами этапа.
- TypeScript / Vite: **build passed** по существующему lockfile. `pip check`: **passed**. Среда: Windows, Python 3.14.5, Node 24.16.0, pnpm 11.25.0; Python-пакеты закреплены отдельным файлом ограничений.
- Browser preview, запуск API, HTTP-контракты, Telegram-подпись, реальные уведомления и production в этом этапе **не проверялись**. Старые заявления о браузерных прогонах не считаются новой проверкой.

## Воспроизведённые проблемы и согласованный следующий шаг

- Замена силового A на новое силовое B сохраняет `Exercise.id`: при явно заданных для B 20 кг рекомендация использует 80 кг из A. После любого из трёх временных типов новое силовое B получает 0 вместо 20 кг. В цепочке A (80 кг) → кардио → новое силовое C (старт 30 кг) получается 40 кг из медианы 80 и технического нуля. Для A и B аналитика возвращает одну серию вместо двух. Все числа — синтетические тесты `tests/test_history.py`, не данные пользователя.
- ПДО назначения хранится, но при создании занятия побеждает фаза / возвращение. Допустимый ПДО 0 также теряется в `rir_target or 2`. Справка называет базой последнюю обычную тренировку, хотя алгоритм использует медиану первых рабочих весов до трёх занятий. Эти две статические находки не исправлялись и не включены в число шести регрессий.
- Согласовано пользователем 01.11.2026: сохранить приоритет ПДО фазы и возвращения; позже устранить неоднозначное поле редактора. Все уже созданные занятия при постоянной замене должны сохранять прежнее движение; интерфейс должен явно сообщать, что замена действует со следующего нового занятия.
- Этап 0 меняет только тесты, ограничения сравнимого окружения и документацию. API, модели, миграции, формулы, UI, webhook и расписания продукта не изменены. Правки совместимы с независимыми ветками без миграции данных; общие fixtures и время тестов при интеграции нужно сохранить. PostgreSQL пока остаётся непроверенным.
- Следующий продуктовый этап — безопасная постоянная замена с отдельной идентичностью назначения, явным стартом и сохранением истории. Выбор продолжения старой базы при возврате к движению и точный API-контракт согласуются до реализации. Разрешения на реализацию этапа 1, PR, публикацию, слияние или deployment пока нет.
